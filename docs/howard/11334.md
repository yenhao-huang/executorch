# Portable kernel: avg_pool2d_backward.grad_input

Related issue: [ExecuTorch #11334](https://redirect.github.com/pytorch/executorch/issues/11334)

## Summary

The portable library had no kernel for
`avg_pool2d_backward.grad_input`, and neither `functions.yaml` registered it.
This adds `op_avg_pool2d_backward.cpp`, which matches ATen CPU semantics for
unbatched `(C, H, W)` and batched `(N, C, H, W)` inputs. It supports
`kernel_size`/`stride`/`padding` given as one or two values, an empty `stride`
(defaults to `kernel_size`), `ceil_mode`, `count_include_pad`, and
`divisor_override`. The schema was checked against torch `2.14.0+cpu`:

```text
aten::avg_pool2d_backward.grad_input(Tensor grad_output, Tensor self, int[2] kernel_size, int[2] stride, int[2] padding, bool ceil_mode, bool count_include_pad, int? divisor_override, *, Tensor(a!) grad_input) -> Tensor(a!)
```

The issue thread had no comments, no assignee, and no linked work, and
upstream main (`ec5e3cf21f`) had no kernel or registration for this op.

## Design

The kernel follows the structure of `op_max_pool2d_with_indices_backward.cpp`:
a local argument check, then `resize_tensor(grad_input, input.sizes())`, then a
dtype switch. It reuses `check_avg_pool2d_args` and
`get_avg_pool2d_out_target_size` from `kernel_ops_util`, adding these checks:

- `grad_output` must have the input's dtype, rank, and the forward output shape.
- The stride is validated explicitly. `check_avg_pool2d_args` passes
  `kernel_size` to `stride_is_valid`, so a zero stride would otherwise get
  through.
- The padded size cannot be smaller than the kernel. This is the same guard
  `avg_pool1d` uses, because the truncating division in
  `_kernel_output_size_helper` would otherwise accept invalid shapes (for
  example H=1, k=3, s=3).
- All three tensors must use the default dim order.

The gradient is computed as a gather rather than a scatter. Each `grad_input`
element adds `grad_output / divisor` from every window that covers it. The
divisor depends on the window and factors into a height extent times a width
extent, using the same window bounds as the forward kernel. As a result,
`grad_input` is fully overwritten (no stale arena contents, no zero-fill), and
Half/BFloat16 accumulate in float like `op_avg_pool2d.cpp`. Supported dtypes
are Float, Double, Half, BFloat16 and Long, matching ATen CPU (Int raises in
ATen too). For Long, each window's contribution uses integer division before
summing, as ATen does.

## Behavior difference from ATen

ATen CPU accumulates Half/BFloat16 gradients in the reduced type. This kernel
accumulates in float, so for heavily overlapping windows in Half/BFloat16 it
can be more accurate than ATen rather than bit-identical. For example,
`HalfAccumulatesInFloat` expects 2052 where a Half running sum stays at 2048.
That test runs only in the portable build (`#ifndef USE_ATEN_LIB`). Float,
Double and Long match ATen exactly or within the default tolerance.
