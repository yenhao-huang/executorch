# Portable kernel: col2im.out

Related issue: [ExecuTorch #11327](https://redirect.github.com/pytorch/executorch/issues/11327)

## Summary

The portable library had no kernel for
`aten::col2im.out(Tensor self, SymInt[2] output_size, int[2] kernel_size,
int[2] dilation, int[2] padding, int[2] stride, *, Tensor(a!) out)`. This
adds one that matches ATen CPU semantics: batched `(N, C*kH*kW, L)` and
unbatched `(C*kH*kW, L)` inputs are folded into `(N, C, H, W)` and
`(C, H, W)` outputs, overlapping blocks are summed, and padding, dilation
and stride are honored.

The issue had no comments, assignee, or linked PR when work started, and
upstream main (`ec5e3cf21f`) had no `op_col2im.cpp` or `functions.yaml`
entry.

## Implementation

`kernels/portable/cpu/op_col2im.cpp` validates its arguments in the same order
and under the same conditions as ATen's `col2im_shape_check`:

- all five parameter arrays have length 2;
- kernel size, stride and dilation are positive, padding is non-negative,
  and the output size is positive;
- the input is 2D, or 3D with an optionally empty batch, with non-empty
  channel and block dimensions;
- the channel dimension is divisible by `kH * kW`;
- each spatial dimension yields at least one sliding block, and `L` equals
  `blocks_h * blocks_w`;
- input and output have the same dtype and the default dim order.

Beyond ATen, the portable kernel also rejects an `output_size` value that does
not fit in the 32-bit `SizesType` (otherwise the resize would narrow it while
the loops still used the full value and wrote past the output buffer), and
any int64 overflow in `kH * kW`, `output_size + 2 * padding`,
`dilation * (kernel_size - 1)` or the block count. ATen raises for the
overflowing kernel product too, but it wraps on the padding sum.

The output is resized to the computed shape, so dynamically bounded outputs
work. Rather than scattering from the columns as ATen does, the kernel loops
over output pixels and gathers every `(kh, kw, block)` that covers each one.
This lets Half and BFloat16 accumulate in a float register without a scratch
buffer. Supported dtypes are Float, Double, Half and BFloat16. ATen also
accepts complex types, which the portable float switch does not cover.

Registration follows the existing portable kernels: `kernels/portable/functions.yaml`,
`kernels/aten/functions.yaml`, `build_variables.bzl`, `op_registration_util.bzl`,
`kernels/test/CMakeLists.txt` and `kernels/test/targets.bzl`.

`OpCol2ImOutTest` ran 25 cases and all 25 passed, as `LastTest.log` shows.

`HalfAccumulatesInFloat`, `NonDefaultDimOrder`, `OutputSizeExceedsSizesType`
and `PaddingOverflows` run only in the portable build (`#ifndef USE_ATEN_LIB`).
ATen accumulates Half in Half, so the float accumulation result is portable-specific: `1000.5`/`1001` rather than ATen's
`1000.0`/`1000.5` for that input.

## Not verified

- Buck build: the targets are registered, but only CMake was run.
- The ATen-mode test build (`USE_ATEN_LIB`).
- Full `lintrunner`.
- Performance.
- Complex dtypes, which ATen supports and the portable kernel rejects.

Passing locally does not guarantee that CI will pass.
