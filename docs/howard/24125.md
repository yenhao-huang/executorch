## 2. Diagnosis and solution

`aten.index.Tensor` lowers through `builders/op_index.py` to QNN Gather;
`op_gather.py` handles another operator. Captured metadata shows UFIXED_POINT16
tables `[2048,128]`, int32 indices `[320]`, gathered values `[320,128]`, then
reshape to `[1,320,128]` for broadcast against `[6,320,128]`. Table/gather scale
is about `3.0518044e-05`, offset `-32768`. Wrapper reuse, quantization, consumer
shapes and BMM layout are consistent. Output dequantization and runtime buffer
binding were inspected. No evidence establishes lifetime corruption or aliasing.

Running the extracted context directly through SDK `qnn-net-run`, using
`--backend .../libQnnHtp.so --retrieve_context .../forward_0.bin
--input_list .../input_list.txt --use_native_input_files`, produces all outputs
**bitwise identical** to ExecuTorch (`../logs/baseline-2.51/sdk-boundary.json`).
The fault is localized to the compiled QNN graph/SDK boundary. The proprietary
SDK's internal root cause is not proven.

The fix uses GatherNd only on HTP for axis-zero indexing of a two-dimensional
UFIXED_POINT16 table by a vector. Reshaping `[N]` indices to `[N,1]` and using
`batch_dims=0` preserves row-selection semantics, table data, output shape and
quantization. Other dtypes, ranks and axes keep their existing lowering. Both
SDK op definitions support these types. As for Gather, indices must be in range.
No full-head tiling, extra graph output or consumer-count condition is introduced.

Diagnostics:

- Removing broadcast reshaping or moving Gather to axis one of a rank-three
  table still fails (0.7683357). The latter is outside this fix's demonstrated scope.
- Full-head tiling passes, but expands tensors unnecessarily.
- Multiply-only output fails (0.6459853) and passes with the fix (0.0000620).
- Dumping all intermediates promotes tensors to APP_READ and hides the failure;
  this is not acceptance evidence. Wrapper capture only reads metadata.
- A single **output-only** RoPE fails (0.8566374), then passes (0.0012154).
  The reporter's unspecified single-RoPE control may differ; sharing two consumers
  is not a necessary trigger.

## Independent review revision — 2026-10-29

Parent's Claude CLI review examined head `6348763a18dd5511b293cbbe87fa7315c8930888`.
Its confirmed P2 is legitimate: the original workaround selected GatherNd on
LPAI too, which supports Gather but rejects GatherNd with SDK error 6005.
This drops a previously delegated index to CPU. Parent independently reproduced
one delegate on baseline and zero on the reviewed revision. This worker added a
registered regression and reproduced the same four failures before correction.

The correction propagates backend type through visitor construction. The factory
requires it explicitly; both QnnOperatorSupport (also used by the LPAI fallback
pass) and QnnBackend preprocessing supply it from their compiler options. Custom
visitors and all factory callers also receive it. Direct NodeVisitor construction
for metadata helpers defaults to Undefined, not an implicit HTP selection. Only
`kHtpBackend` enables the workaround; LPAI retains its supported Gather lowering.

`test_qnn_backend_index_table_16bit` uses an activation table `[64,32]` and indices
`[5,0,5,63]`, testing 16a8w/16a16w with both input and static indices. Each case
requires one QNN delegate and successful SDK compilation. HTP additionally runs
the emulator and compares every element to QDQ with `atol=rtol=1e-3`. This expands
coverage of the actual GatherNd branch; the older rank-three/8-bit index tests
only exercise the unchanged Gather path.

**LPAI numerical limitation:** attempting execution exposed a separate failure
for this table shape. The original `390bc0618f` Gather method loaded in memory
produces the same four numerical failures. Therefore the LPAI regression checks
real SDK compilation and delegation, not numerical execution. It is not skipped,
and a CPU fallback fails its delegate-count assertion. The reviewed-head method
still fails all four delegation cases under this final configuration. No SDK
unsupported-op error is suppressed. Numerical LPAI correctness is not claimed.
